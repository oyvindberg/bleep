Bleep — a build tool for Java, Kotlin & Scala

Everything got faster.
Except the build.

Coding agents write at a thousand words a minute, fan out into six git worktrees, and then sit there, watching a build tool configure itself. We build five million lines of JVM code for a living and we got tired of waiting too. So we built a build tool with a native binary that bootstraps in ten milliseconds, answers an agent in 265 tokens at worst, and forks a warm copy of your entire compiled world in under a minute. Why speed is the whole game

A build minute costs more than a minute.

You know this one from the inside: you hit compile, it takes forty seconds, you glance at Slack, and twenty minutes later you remember what you were doing. The research agrees with your gut. Parnin studied ten thousand programming sessions: after an interruption, the median programmer needs 10–15 minutes to make the next edit. GitHub priced the waiting at roughly $400 of developer time per slow build. And the agent era sharpened it: code generation exploded while merged throughput didn’t — validation is the bottleneck now, and the build sits in the middle of every validation. DORA’s verdict: AI multiplies the conditions you already have. Teams with fast feedback loops turned agents into 20–30% gains. Teams without got a faster way to wait.

The build is the heartbeat of the loop.
It should be too fast to notice.

Field notes

Everyone can see the problem.

We didn’t invent the pain. Here it is in the ecosystem’s own words, links included — and what falls out when the build tool is designed for it instead of patched around.

The daemon that logs itself to death

An open Gradle issue, verbatim title: “daemon hangs unrecoverably if it receives console output too fast”. A build daemon taken down by its own log volume. Bleep’s daemon emits typed events; the transcript lands on disk as data, and the terminal gets a live summary, not a firehose.

Teams ship software to hide their build’s output

Agent-infra companies build custom backpressure wrappers so Maven and Gradle logs (“notoriously verbose”, their words) stop shredding agent context. An entire product category exists to apologize for build output. Bleep’s worst answer measures265 tokens, because that’s all it says.

MCP servers that read about your build

Gradle’s enterprise Develocity MCP server is analytics over build scans — it tells agents about builds. Maven and Bazel get third-party wrappers that re-parse CLI text. Bleep is the MCP server: compile, test, run, diff. Built in, free, and it does the work.

Is your stack in?

Java, Kotlin, Scala — first-class.

The question right after the numbers: is my thing supported? Compile, test, run, publish, IDE import, cross-build, scripts and sourcegen are first-class for all three languages. The details, honestly labeled:

Java

First-class: javac and ECJ, annotation processors (Lombok, MapStruct, Dagger, Immutables, …), Spring Boot via bleep-plugin-spring-boot, Maven import.
Partial: BOM / dependencyManagement not yet, every dependency declares its own version explicitly.
Not in scope: Android.

Kotlin

First-class: kotlinc 2.x, compiler plugins (allopen, jpa, spring, noarg, serialization), KSP processors (Room, Hilt, Moshi codegen, Koin KSP, kotlin-inject, …), Kotlin/JS via cross:.
Partial: KSP runs from scratch each compile; Kotlin/Native targets exist but the ecosystem expects Gradle; no Gradle import yet — hand-port today.
Not in scope: KAPT (migrate to KSP), Android.

Scala

First-class: Scala 2.13 + Scala 3 cross-builds, Scala.js, Scala Native, scalafmt, scalafix, Zinc incremental, sbt import, ports of sbt-ci-release / sbt-sonatype / sbt-pgp / sbt-dynver / sbt-native-image / mdoc.
Partial: projectMatrix-style third axes beyond JVM/JS/Native × 2.13/3.
Not in scope: publishing as an sbt plugin artifact (consuming sbt plugins works).

How it can be this fast

Simplicity is the weapon.

Your whole build is one YAML file. Not a program that eventually produces a build — the build itself, as data. Everything a build plugin ever did is either source generation or a program you run. That single decision is where all the speed comes from: nothing to configure, nothing to interpret, nothing to warm up, nothing that can hide.

Tenet1

The build is data.

Readable top to bottom by anyone on the team, and by any agent in one pass. Grep it, diff it, rewrite it with tooling. A build you can read is a build you can trust.

Tenet2

Everything else is code.

Docker images, doc generation, release orchestration: programs in your repo, in your language, debuggable in your IDE. Not plugins in someone else’s lifecycle, debugged with println.

Tenet3

Fail loudly.

No graceful degradation, no silently stale outputs, no “it probably worked”. If something is wrong, bleep throws. Humans appreciate this. Agents depend on it — a tool that degrades quietly sends them chasing ghosts.

“But my build plugin!” We checked. We analyzed each of the top 50 Maven plugins, implemented the hardest case (Spring Boot), and ship codebases of millions of lines on this model.

Also: you

The same speed in your IDE and terminal.

Agents run headless. You don’t. Open the project and the IDE import takes a second or two, because bleep reads bleep.yaml and hands the model straight over BSP — no configuration phase, no plugin resolution, no progress bar with your afternoon on it. Switch to a branch with a different Kotlin version and the reload is milliseconds. And when you run tests, you watch them run.

IDE imports in seconds

First import into IntelliJ or any BSP editor: a second or two. Branch reload: milliseconds. In Gradle or sbt the same actions cost a configuration phase, plugin loading, and an IDE model rebuild — minutes, on real projects, several times a day.

Tests run everywhere at once

Suites compile and run in parallel across every CPU, in forked JVMs with their own classpaths. The terminal stays live: which suites are compiling, which are running, which failed — the moment it happens, not at the end.

A summary you can act on

Exact suite and test names, pass/fail counts per project, and bleep test --diff prints only what changed since the previous run — rendered as prose for your eyes, the newly failing test named with its assertion; agents get the same diff as data with --output json. JUnit XML is one flag away for CI.

Where it matters most

Written for the biggest repos out there.

Big repos are where the important software lives — systems with twenty years of history and no appetite for adventure — and where build pain compounds hardest: every wart multiplied by a thousand modules and a hundred engineers. The industrial-strength alternative has a price tag on the record: “Rolling out Bazel at my prior employer took about one person decade of engineering time”. Bleep is designed at scale and lives at scale, daily — with no dedicated build team required.

One hot daemon per machine

Every checkout, every worktree, every IDE window and agent shares one compile server that keeps incremental state hot and stores identical dependency analyses exactly once. Ten worktrees don’t cost ten JVMs.

CI that skips

bleep build invalidated names exactly the projects a diff touched — both build loads are instant, because the build is data. The remote cache pulls everything a previous run already compiled. You pay to build the change, not the repo.

Migration is one command

bleep import reads an sbt build, bleep import-maven a Maven one, and writes the equivalent bleep.yaml — project graph derived, templates inferred. Compiling and testing on day one, even at hundreds of modules.

The agent era

Your agents’ favorite build tool.

Agentic development has a shape: an orchestrator fans subagents into git worktrees, each hammering compile-test loops in parallel. Bleep ships the whole apparatus for that shape, built in. One MCP registration covers every checkout you’ll ever create. Every call names its workspace, so a subagent can’t silently build the wrong checkout. New worktrees clone the parent’s compiled state instead of rebuilding the world. And every run becomes a transcript the agent can query — or diff.

build runs you can diff“what changed since the last green run?” is one call, answered as data. No other build tool has this shape — the nearest attempt, Develocity’s build-scan comparison, is paid analytics in someone else’s cloud.

agentbreaks a test, reruns — diffBase pins the last green run, so the answer rides along
bleep.test { directory: ~/repo/wt/api, diffBase: 18 }→ { historyId: 19, failed: 1, diff: { summary: "1 newlyFailing", newlyFailing: [{ test: "PricingTest.10 percent off at 100 and above", from: "passed", to: "failed", message: "expected 216, obtained 204" }] } } ← run + what-changed in one call: the break, name and assertion, nothing else
agentreverts, reruns
bleep.test { directory: ~/repo/wt/api, diffBase: 18 }→ { historyId: 20, passed: 14, diff: { identical: true, summary: "No logical differences." } } ← ~800ms of timing noise between the runs, zero false diffs

Or just watch it. Twenty-seven seconds: an agent in its own worktree proves its change as a diff — against its previous run, then against the worktree it was forked from.

Answers, not logs

Compile and test return counts, the first errors, and a historyId — a couple hundred tokens. Failures stream the moment they happen. The full transcript is regex-searchable server-side, so no agent ever pipes a build log to a file and greps past the answer again.

Forks start warm

bleep.copy-state clones the parent worktree’s compiled state under the compile server’s own locks — clonefile-fast, safe mid-compile. Fork to verified green in 54 seconds on 5.1 million lines. Subagents earn their keep from the first minute.

The loop is one call

Pass diffBase to compile or test and the response carries what your edit changed: newly failing, fixed, new diagnostics — nothing else. Timing jitter is filtered by construction, so the diff never cries wolf. Humans get the same loop as bleep test --diff.

the whole surface, 18 tools — bleep.compile · test · run · projects · test.suites · build.effective/resolved · history.list/show/diff/diff-timing · copy-state · fmt · clean · sourcegen · scripts · programs · restart

Bleep is developed by sessions of parallel agents in git worktrees, building bleep with bleep. Everything above is how this tool gets maintained, daily.

The part where we admit things

What bleep is not.

Marketing pages that admit nothing are asking you to do the discounting yourself. Save the trip: bleep is for Java, Kotlin, and Scala on the JVM (with JS and Native cross-builds). No Android. No Gradle import yet — Maven and sbt import exist, Gradle is a hand-port today. BOM support is on the list, not in the tool. The status page keeps the full account. If your dealbreaker is on it, we’d rather you find out here than three days in — and if it isn’t, everything above is waiting. One more, in reverse: if bleep ever stops being right for you, your whole build is portable YAML and Maven coordinates — leaving is a mechanical translation, and we didn’t just write the exit strategy down, we implemented it: the repo carries bleep export-maven, and run against bleep’s own build it emits POMs that compile every module and pass the tests under stock Maven — source generators included. That is a run we do by hand, not an automated test, and the guide lists what the exporter does not translate. Betting on a young tool should never mean betting the repo, so the escape hatch is code you can read and run.
