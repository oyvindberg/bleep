
# Memory & Parallelism

When a test, a source generator, or a compile runs out of memory — you see `Java heap space`, an `OutOfMemoryError`, or a process `killed by SIGKILL (exit 137)` — this page is what the build summary links you to. It explains every knob that governs how much memory a build uses and how many things run at once, how bleep's servers share one machine, and how to read what `bleep server top` shows.

## The short version

Two questions, and they belong to different owners:

| question | who decides | where |
| --- | --- | --- |
| how much memory does *this code* need? | the build | `platform.jvmOptions` in `bleep.yaml` — per project, and it sizes **forks** |
| how much of *this machine* may bleep use? | whoever owns the machine | user config: `parallelism`, `compileServerMaxMemory`, `machineScheduling` |

That split is deliberate. A repo cannot know whether it is running on a 16 GB CI container or a 64 GB workstation, and a machine cannot know which of your suites is heavy.

A forked process (a test runner, a sourcegen script, a KSP processor, a native linker) then has **two** costs, and they are controlled separately:

1. **How big each fork is** — its `-Xmx` heap ceiling. If a suite genuinely needs more memory than it is given, it fails with an in-JVM `OutOfMemoryError` naming the suite. **Fix: give that project more heap.**
2. **Whether there is room for it on the machine** — decided by bleep, not by you. Every bleep server on the machine shares one view of its memory and admits a fork only when it fits. You do not configure this; the one thing you can turn is `parallelism`, which is about CPU.

bleep measures what forks actually cost and admits them against what the machine can currently spare, so most of the time you never touch any of this. You reach for these knobs when a specific suite is heavier than the default, or when bleep is sharing the machine with something it can't see.

:::info Version

The machine-wide scheduler described on this page arrived after `1.0.0-M10`. On M10 and earlier, concurrency is a plain count of permits with **no memory dimension** — so on a small machine you must set `parallelism` yourself, because nothing will do it for you.

:::

## Per-fork heap

Every forked JVM is given a default heap of **2 GB**. A fork that states no `-Xmx` is *not* unlimited — the JVM would otherwise take a quarter of the machine, and bleep starts one per core, so a default is essential.

### The build sizes forks, and only forks

`bleep.yaml` has exactly one resource control, and it is per project:

```yaml
projects:
  my-heavy-tests:
    isTestProject: true
    platform:
      jvmOptions: -Xmx4g
```

This is the right and only place for a build to say "this code needs more memory", because that is a property of the code, not of the machine it happens to run on. Everything else about resources — how many things run at once, how big the compile server is — belongs to whoever owns the machine, and lives in user config.

**It applies to forked processes.** `platform.jvmOptions` reaches:

- **forked test JVMs** for that project, and
- **`bleep run`**, unless `jvmRuntimeOptions` is also set, in which case that wins for `run` only.

**It does not affect compilation.** Your code is compiled *inside* the long-lived compile server, in its heap — not in a JVM started for your project. So raising `jvmOptions` will not help a compile that runs out of memory, and lowering it will not make compilation lighter. The compile server's own heap is `compileServerMaxMemory`, in user config.

If that distinction bites, the symptom tells you which side you are on: an `OutOfMemoryError` naming one of *your* test suites is the fork, and `jvmOptions` is the fix; an `OutOfMemoryError` in the build summary with the server dying is the server, and `compileServerMaxMemory` is the fix.

### Precedence for a test fork

A test fork is started with **exactly one `-Xmx`**, chosen from the first of these that states one:

1. `--jvm-opt` on the command line — this run only
2. the project's `platform.jvmOptions` — what this code needs, checked into the build
3. `testRunnerHeap` from user config — the default for projects that state nothing
4. bleep's own default, 2 GB

**`testRunnerHeap` is a default, not a ceiling.** A project that sets `-Xmx` in `platform.jvmOptions` overrides it, in either direction — a project may ask for *more* heap than the machine-level setting, and it gets it:

```yaml
# user config says testRunnerHeap: 1g …
projects:
  my-heavy-tests:
    isTestProject: true
    platform:
      jvmOptions: -Xmx4g    # … and this suite still forks with 4 GB
```

That is the right way round: how much heap a suite needs is a property of the code, and the code is what lives in the repo. Nothing silently shrinks a heap the build asked for. What protects the machine from one project asking for a lot is *admission* — the scheduler charges a fork its whole heap until it has measured it, and will run an oversized one on its own rather than alongside others — not clamping.

To see what a fork was actually given, `bleep server config show` prints the configured default, and the test view reports each fork's heap. If you want to check from inside a suite, `Runtime.getRuntime.maxMemory` is the number that settles it. Do **not** test this by setting an absurdly small `-Xmx` and expecting a crash: the JVM quietly rounds a too-small heap up to something it can start with, so `-Xmx3m` proves nothing.

:::info Renamed

`testRunnerHeap` was called `testRunnerMaxMemory`, and `bleep server config test-runner-max-memory` is now `bleep server config test-runner-heap`. The old name never was a maximum — a project's own `-Xmx` has always outranked it. Existing config files and the old command keep working.

:::

### The other forked processes

Sourcegen scripts and KSP runners are sized in user config, since they are bleep's own tooling rather than your code:

| Setting | Sizes |
| --- | --- |
| `testRunnerHeap` | test runner JVMs, for projects that state no `-Xmx` of their own |
| `sourcegenMaxMemory` | sourcegen scripts |
| `kspRunnerMaxMemory` | KSP (Kotlin symbol processing) runners |
| `compileServerMaxMemory` | the compile server itself — **not** a fork; the long-lived heap your compiles run inside |

## How many run at once

One knob: **`parallelism`** — how many CPU slots *one compile server* may hold at once. It defaults to one per core and covers everything the scheduler runs for that server: compiles, links, test suites, sourcegen scripts, annotation-processor and KSP resolution. A compile holds a slot while it runs; a fork holds slots only while work runs on it (a batch fork as many as suites it runs at once); a warm fork between suites holds none.

It is **CPU only, and per server.** Memory is not what it controls — the scheduler decides memory machine-wide on its own, below — and it is not shared between servers: two servers on one machine (two bleep versions, two JVMs) may each hold their own `parallelism` slots. That is deliberate: a slot is cheap to over-subscribe for a moment, memory is not, and the two are kept apart so that lowering one never silently changes the other.

```bash
bleep server config parallelism 2
bleep server config parallelism-clear   # back to one per core
```

`parallelismRatio` expresses the same thing as a fraction of cores (`0.5` for half) if you prefer that in a config file shared across machines of different sizes.

Lowering parallelism is the fix when the machine is being *overwhelmed on CPU* — everything is slow because too much is running — not when forks are being killed. Memory is the scheduler's job (next section), and lowering parallelism to protect memory only leaves cores idle.

### Setting it for a CI job

There is deliberately **no environment variable** for this, and no per-invocation flag. The compile server is shared: it reads `parallelism` from user config and applies a change to its next decision, so a per-client override would mean whichever client happened to start the daemon silently configured it for everyone else — including runs that had no opinion. The same goes for the server's own heap, which is part of the key that decides *which* daemon you get: two different values would quietly give you two daemons.

A CI job is one machine, so configure the machine, as a step before you build:

```yaml
- name: Configure bleep for this runner
  run: |
    bleep server config parallelism 2
    bleep server config max-memory 4g

- name: Test
  run: bleep test
```

That writes the same user config a developer would keep, which is what a fresh runner wants: it has no standing preferences, so state them once and let every later invocation agree.

## How the machine's memory is shared

You never configure this, but it explains why bleep sometimes runs fewer forks than the raw numbers suggest — and why it never runs *more*.

Every bleep server on the machine runs the same **machine scheduler**. Memory is decided machine-wide, for forks only; compiles run inside the server's own heap, which is already part of the machine's used memory, and never wait for memory room (they wait for a CPU slot, and for the server's own heap gate when that heap is nearly full).

**The ceiling.** Forks may fill the machine's memory up to a ceiling: physical memory minus a headroom bleep keeps free for everything that is not a fork — the OS, your IDE, a browser, the servers' own heaps growing. The headroom is `max(4 GB, RAM/8)` and is not a user setting.

**What counts.** The machine's *used* memory is read from the OS each time a server wants to start a fork — every process, bleep's or not — so a browser opened mid-build simply leaves less room. A fork that has just started is charged its full heap plus overhead until the scheduler has measured it, a second later; from then on it is charged what it actually uses. A 2 GB-ceiling fork that only ever uses 600 MB is counted as 600 MB after that first second, so many more fit than the ceilings would suggest.

**One guarantee.** A command with nothing running gets one working fork, always — whatever the room, whatever other servers are doing. A build never stalls completely because the machine is full; it slows down to one fork and continues. Beyond that guarantee, forks are admitted as room allows, one new fork per tick per server, oldest request first.

**Processes a toolchain spawns.** A Scala Native link runs clang and the linker itself, many at once; bleep attributes those processes to the link — every one of them names the link's work directory — and charges the link the sum of what they use. A process bleep cannot place with any fork is said so in the server log; it still counts in the machine's used memory, so nothing is over-admitted because of it.

**Warm forks first.** A test fork that has finished its suite is kept warm for the next suite of the same shape rather than killed and restarted; the scheduler reuses a warm fork before it starts a new one, and evicts warm forks that nothing will reuse, or that stand in the way of a fork that is needed now, oldest first.

**Pressure.** Besides used memory, the scheduler reads the OS's own memory pressure signal (macOS's memory pressure level, Linux PSI, Windows memory load). Under *elevated* pressure no new forks start beyond the guarantee; under *critical* pressure every idle warm fork is also evicted. On a platform with no pressure signal the scheduler says so once in the server log and schedules on used memory alone.

**Shared through a lock.** Every server reads the others' state and claims memory under one lock, held for microseconds. If another server holds it for longer than a second — stuck, or on a stalled disk — the waiting server still gets its guarantee and its warm reuse, and `bleep server top` names the holder.

### When memory is needed elsewhere

Two things make a server give memory back without being asked by its own work: the OS reports elevated pressure, or another server publishes that it has work it could not admit. Low memory with nobody waiting is neither — a warm server is not thrown away for nothing.

- A **busy** server sheds the cached builds and compile analyses of every workspace it has no request for. The cost is a cold load next time that workspace is used; nothing about correctness changes.
- An **idle** server — no client connected, nothing scheduled, and idle for five minutes — shuts itself down, so the next command starts a fresh one. One server yields at a time, the longest idle first. An IDE connected through `bleep bsp` keeps its server, since the IDE would otherwise see the build server disconnect; an MCP server does not need to, since `bleep mcp-server` reconnects on every tool call.

### Opting out

If a machine should not take part — a CI runner that is bleep's alone, or a platform bleep cannot measure — a server can run **unconstrained**:

```bash
bleep server config machine-scheduling unconstrained
bleep server config machine-scheduling-clear   # back to cooperative
```

Unconstrained means no memory room, no pressure brake, no lock: `parallelism`, the server's heap gate, warm reuse and the one-fork guarantee are all that remain. A server that cannot measure its machine (an OS or architecture the probes do not support) runs unconstrained whether or not you asked, and says so in its log and in `bleep server top`.

## Small machines and CI

The compile server's heap and the forks' footprints come out of the same physical memory, and the headroom is held back for everything that isn't a fork. It is worth doing the arithmetic once, because the failure mode is forks queueing rather than anything that names memory.

On a 16 GB runner the ceiling for forks is 12 GB (16 minus the 4 GB headroom), and the server's own heap is part of what is *used* under it:

| server heap | used by the server (roughly) | room for forks | what fits |
| --- | --- | --- | --- |
| 8 GB | ~8 GB | **~4 GB** | one or two forks, serialised |
| 4 GB | ~4 GB | **~8 GB** | two or three 2–3 GB forks |
| 2 GB | ~2 GB | **~10 GB** | three or four 2–3 GB forks |

The trap is asking for a big compile server *and* big forks on a small box: an 8 GB server on 16 GB leaves little under the ceiling, so forks queue behind each other and the job takes far longer than the numbers suggest. On a 16 GB runner, a 4 GB server is usually the better trade.

Two rules of thumb for CI:

1. **Size the server first.** It is long-lived and shared; the forks divide what's left.
2. **Set `parallelism` to the cores you actually have.** A CI runner often advertises more cores than it will give you steadily; the default is one slot per advertised core.

## How the knobs trade off

They are not independent — think of it as *peak memory ≈ per-fork heap × forks running at once*, bounded by what the machine can spare.

- **Raising per-fork heap** lets a heavy suite pass, but each fork is charged more until measured, so **fewer start at once** — effective parallelism drops until the measurements come in.
- **Raising parallelism** lets more run at once, but only if there is memory room for the forks; past that point the extra slots sit unused while forks wait for room.
- **Lowering per-fork heap** lets more run in parallel, but a suite that needed the headroom will `OutOfMemoryError`.

The practical recipe:

1. **A single suite fails with `Java heap space` / `OutOfMemoryError`.** That suite needs more heap. Give *that project* a larger `platform.jvmOptions: -Xmx…`. Don't lower parallelism — the rest of the build is fine.
2. **Forks are killed by `SIGKILL (exit 137)`.** The machine ran out of memory anyway: something bleep cannot see took it, or a fork grew far past its measured size between two measurements. `bleep server top` shows the machine's used memory against the ceiling and the pressure level at the time; the fix is usually a smaller server heap or a smaller per-fork heap on that machine, not a lower parallelism.
3. **The build is slow and `top` shows forks waiting for memory.** The machine is full. Lower the server heap, lower a too-generous per-fork heap, or close what else is using the memory.

## Reading the diagnostic

bleep distinguishes who did the killing, because it matters for the fix:

- **`Java heap space` / `OutOfMemoryError`** — the fork hit *its own* `-Xmx` ceiling. Raise that project's heap (recipe 1).
- **`killed by SIGKILL (exit 137), not by bleep`** — the *OS* killed it, almost always memory pressure. Reduce concurrent memory (recipe 2/3). Check your system log for a memory-pressure kill to confirm.
- **`terminated by bleep (…reason…)`** — bleep itself killed it, and the reason is stated (a suite timeout, a cancellation, the scheduler evicting a warm fork for room). Not a memory problem; read the reason.

## What `bleep server top` shows

The dashboard's summary puts bleep's use in proportion to the machine, then one line for the scheduler:

```
Machine  12.0 GB used of 40.0 GB fork ceiling (48.0 GB − 8.0 GB headroom), 2.5 GB pending for starting forks — pressure normal
```

*Used* is the machine's memory as the scheduler's probe reads it, every process included; *pending* is what forks that have started but not yet been measured are charged; *pressure* is the OS's level, or "no pressure signal" and why. Servers running unconstrained are named with their reason, and so is a server that could not get the lock and who held it.

Per server, the **Overview** tab shows CPU slots in use of that server's `parallelism`, the machine memory gauge, how many forks it holds (measured against still starting), and the lock's last outcome. The **Activity** tab lists what runs in the server's heap, each fork with its charge — `starting, charged 2560 MB bound` until measured, then `measured 1200 MB (bound 2560 MB)` — whether it is busy or warm, and what is waiting for a slot or for memory. The **Processes** tab measures the same forks from outside, by pid, so a gap between the scheduler's charge and the process's real footprint is visible.
